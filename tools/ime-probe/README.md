# ime-probe — 한글이 셸에 온전히 닿는지 잰다

```sh
sh tools/ime-probe/run.sh
```

진짜 WKWebView를 세우고, 진짜 두벌식 입력기를 켜고, 물리 키코드로 쳐 넣은 뒤,
**xterm이 PTY로 내보낸 바이트**를 읽어 기대값과 맞춘다. 통과하면 이렇게 나온다:

```
한글 조합 계측 — 창이 앞으로 나오고 입력 소스가 잠깐 바뀝니다
  ok    안녕 + space           C548 B155 0020
  ok    안녕 + Enter           C548 B155 000D
  ok    안녕 + BS 2회          C548 3134 000D
  ok    했다 (Shift)           D588 B2E4 000D
  ok    안녕 (0폭 칸)          C548 B155 000D
  ok    영문 hello             0068 0065 006C 006C 006F 000D
  ok    조합 표시 (안녕)       active=true text="녕" 자리맞음=true
  ok    조합 표시 (끝난 뒤)    active=false text="" 자리맞음=n/a
  ok    에코 뒤 자리 회복      ok
  ok    0폭 준비가 됐는가      inline=0px
```

## 왜 이게 있나

이 판이 고친 한글 조합은 **웹뷰·입력기·xterm이 만나는 자리**에 있어서 `pnpm test`가 못 닿는다.
그 자리를 사람이 손으로 확인하면 매번 「한글을 쳐 보고 눈으로 읽는」 일이 되고, 화면에서 읽은
자모는 글꼴 폴백을 타서 **증거가 되지도 못한다**. 그래서 바이트를 잰다.

무엇이 원인이었고 무엇을 배제했는지는 `docs/ime-probe.md`에 있다.

## 열 대본이 각각 지키는 것

| 대본 | 지키는 것 |
|---|---|
| 안녕 + space | 낱자가 아니라 완성 음절이 나가는가. 스페이스가 U+0020인가(U+00A0으로 오던 적이 있다) |
| 안녕 + Enter | 개행보다 앞 음절이 **먼저** 나가는가 |
| 안녕 + BS 2회 | 조합 중 백스페이스가 꼬리를 줄이는가 (`녕`→`녀`→`ㄴ`) |
| 했다 (Shift) | 수식키 keydown이 앞 음절을 흘려보내지 않는가. 안 막으면 `해했다`가 나간다 |
| 안녕 (0폭 칸) | 커서가 넓은 글자 뒤칸일 때 — xterm이 인라인 `width: 0px`을 쓰는 자리다 |
| 영문 hello | 영문이 한 타에 한 자씩, 안 붙들리고 나가는가 |
| 조합 표시 (안녕) | 붙들고 있는 글자가 커서 자리에 겹쳐 보이는가 |
| 조합 표시 (끝난 뒤) | 조합이 끝나면 걷히는가 |
| 에코 뒤 자리 회복 | 흘려보낸 음절의 에코가 커서를 옮긴 뒤 표시가 **따라가는가**. 안 따라가면 방금 확정된 음절 위에 겹쳐 남는다 |
| 0폭 준비가 됐는가 | 위 「0폭 칸」 대본이 **정말 그 자리를 만들었는지**. 준비가 조용히 안 돌면 그 대본이 아무것도 안 지킨다 |

## CI에 못 거는 이유

창을 앞으로 끌어오고 **입력 소스를 바꿨다 되돌린다**. GUI 세션이 필요하고, 키 이벤트를
던지므로 터미널 앱에 손쉬운 사용 권한이 있어야 한다. 헤드리스에서는 못 돈다.

두벌식이나 ABC가 **켜져 있지 않으면** `!! 입력 소스가 켜져 있지 않다: …`로 끝난다
(시스템 설정 ▸ 키보드 ▸ 입력 소스). `^C`·`SIGTERM`·`SIGHUP`으로 끊겨도 입력 소스는 되돌려
놓는다 — **강제 종료(`SIGKILL`)와 크래시는 못 막는다.** 그때는 손으로 되돌려야 한다.

## 무엇으로 이뤄져 있나

| 파일 | 하는 일 |
|---|---|
| `run.sh` | 앱 모듈을 번들하고 `src/index.css`의 실제 규칙을 떠 와서, 열 대본을 돌린다 |
| `entry.ts` | 계측기가 앱에서 가져다 쓰는 것들. **손으로 베끼지 않기 위해** 있다 |
| `probe.swift` | WKWebView + 입력 소스 전환 + 물리 키 주입. 인자: `<page.html> [키코드…] [ascii] [wide]` |
| `page.html` | 앱의 옵션·테마·조합 다리로 세운 xterm 한 벌. `onData`로 나간 것을 찍는다 |

**흉내가 아니라 앱의 코드를 쓴다** — `run.sh`가 `src/`에서 모듈과 CSS 규칙을 그때그때 가져온다.
그래서 고침을 되돌리면 이 검사가 빨개진다. 실측한 되돌림 둘:

```
수식키 가드를 뺀다   → FAIL  했다 (Shift)   D574 D588 B2E4 000D    (= 「해했다」)
크기 바닥을 지운다   → !! index.css에서 숨은 입력칸의 크기 바닥 규칙을 못 찾았다
```

애드온(fit·web-links·webgl)은 안 붙인다 — 셋 다 입력 경로에 안 닿고, 렌더러가 무관하다는
것은 1판이 이미 실측했다. `scrollback`·`minimumContrastRatio`만 `createInstance`에 리터럴로
박혀 있어 `page.html`에 옮겨 적었다(조합과 무관함은 번들 전수 검색으로 확인).

## 대본을 늘리려면

`run.sh`의 `check`(셸에 닿은 바이트) 또는 `line`(그 밖의 보고 줄) 줄을 늘린다. 키코드는 **물리 키**다(두벌식 `안녕` = `d k s s u d`):

```
d=2  k=40  s=1  u=32  g=5  o=31  t=17  e=14
space=49  return=36  backspace=51
접두사:  s = Shift와 함께,  c = ⌘와 함께     (예: s17 = Shift+ㅅ = ㅆ)
꼬리표:  ascii = 영문 배열로,  wide = 커서를 넓은 글자 뒤칸에 세우고 시작
```

기대값은 **코드포인트로 적는다.** 개행(`000D`)도 U+00A0도 눈에 안 보이는데, 이 판이 고친 것
중 하나가 「스페이스가 U+00A0으로 오던 것」이다 — 보이는 글자로 비교하면 그 회귀가 조용히
통과한다.
